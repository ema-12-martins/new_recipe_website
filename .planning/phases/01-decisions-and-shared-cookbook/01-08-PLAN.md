## Bounded disposable validation-service contract

This contract is part of the plan before any endpoint provisioning or task precondition is considered. It specifies test behavior only; it does not select a vendor, framework, or production service.

**Isolation, health, and reset**
- The trusted test runner receives `TEST_CONTROL_BASE_URL` and `TEST_CONTROL_TOKEN` as environment variables. It invokes exactly `POST ${TEST_CONTROL_BASE_URL}/__test/reset` with Authorization uses the standard bearer-token scheme; its token value is read from the trusted runner's TEST_CONTROL_TOKEN environment variable. Success: `204`; absent/invalid token: `401`; environment not marked disposable: `403`. Reset is idempotent and deletes only the synthetic tenant.
- Neither `TEST_CONTROL_BASE_URL` nor `TEST_CONTROL_TOKEN` is exposed to browser-delivered code, browser storage, browser requests, URLs, logs, screenshots, or evidence. The test-control origin is inaccessible from browser-delivered code; the token is never included in client assets.
- `SPIKE_API_BASE_URL` must be HTTPS and isolated from all production tenants/data. Only synthetic identities, recipes, invitation addresses, and test messages are allowed.
- `GET /health` returns `200 application/json` with `{"service":"family-cookbook-validation","environment":"disposable","resettable":true}`.

**Signup, email verification, sign-in, and session**
- `POST /auth/signup` request `{"email":"synthetic-address","password":"test-only-secret"}` → `202 {"userId":"…","email":"…","verificationRequired":true}` and no session; malformed fields → `400 VALIDATION_ERROR`; duplicate address → `409 CONFLICT`.
- `GET ${TEST_CONTROL_BASE_URL}/__test/mailboxes/{mailboxId}/messages` is called only by the trusted test runner; Authorization uses the standard bearer-token scheme; its token value is read from the trusted runner's TEST_CONTROL_TOKEN environment variable. The runner receives `TEST_CONTROL_BASE_URL` and `TEST_CONTROL_TOKEN` from its trusted environment, and neither value is exposed to browser-delivered code. It returns `200 {"messages":[{"to":"…","kind":"verify-email","verificationUrl":"…"}]}`. Use only synthetic sink addresses. Follow the one-time URL in the test browser; never place its token in evidence.
- `POST /auth/verify` request `{"token":"one-time-test-token"}` → `200 {"verified":true,"userId":"…"}` plus `Set-Cookie: …; HttpOnly; Secure; SameSite=Lax`; invalid, expired, or replayed token → `400 INVALID_OR_EXPIRED_VERIFICATION`.
- `POST /auth/signin` request `{"email":"…","password":"…"}` → `200 {"userId":"…","email":"…","verified":true}` plus the same HttpOnly/Secure/SameSite=Lax session cookie; bad credentials → `401 INVALID_CREDENTIALS`; unverified identity → `403 EMAIL_NOT_VERIFIED`.
- Browser API calls authenticate with the cookie (`credentials: include`); no access/refresh bearer token is returned to page JavaScript or stored in web storage. `POST /auth/signout` clears the cookie and returns `204`; no valid session → `401 UNAUTHENTICATED`.

**Cookbook, invitation, recipe, and removal-review endpoints**
- Authenticated `POST /cookbooks/bootstrap` with `{}` → first verified identity `201 {"cookbookId":"…","role":"owner"}`; same owner's retry `200` with the same cookbook/role; another uninvited identity `403 INVITATION_REQUIRED`.
- Owner `POST /invitations` request `{"email":"synthetic-invitee-address","expiresInDays":7}` → `201 {"invitationId":"…","status":"pending","expiresAt":"…"}`. Owner `POST /invitations/{id}/resend` with `{}` → `200 {"invitationId":"…","status":"pending"}`. Owner `POST /invitations/{id}/revoke` with `{}` → `200 {"invitationId":"…","status":"revoked"}`.
- Invitee `POST /invitations/{id}/accept` with `{}` and a verified session → exact invited-email match `200 {"cookbookId":"…","role":"member","status":"accepted"}`; mismatch `403 INVITED_EMAIL_MISMATCH`; expired/revoked invitation `410 INVITATION_UNAVAILABLE`; unknown ID `404 NOT_FOUND`.
- Authenticated `GET /recipes` → `200 {"recipes":[…]}`. `POST /recipes` accepts `{"title":"…","ingredients":["…"],"instructions":["…"]}` → `201 {"recipe":{…}}`. `PATCH /recipes/{id}` accepts those same fields → `200 {"recipe":{…}}`. Actor and cookbook scope come only from the authenticated session, never a client-supplied cookbook ID.
- Owner `GET /members/{memberId}/removal-review` → `200 {"memberId":"…","affectedRecipes":[{"recipeId":"…","originalCreatorId":"…","editedByOtherMember":true}]}`. Owner `POST /members/{memberId}/removal-review/commit` accepts `{"decisions":[{"recipeId":"…","choice":"keep|remove"}]}` → `200 {"memberId":"…","access":"removed","keptRecipeIds":["…"],"removedRecipeIds":["…"]}`. Only listed affected recipes explicitly marked remove are removed in this one-time member-access workflow; no general recipe-delete endpoint or UI is part of the contract.

**Stable response semantics**
- Every error is `application/json {"error":{"code":"…","message":"…","requestId":"…"}}`.
- Invalid JSON/fields: `400 VALIDATION_ERROR`; missing/invalid session: `401 UNAUTHENTICATED`; signed-in non-owner on all invitation/removal endpoints: `403 OWNER_REQUIRED`; wrong verified invitee: `403 INVITED_EMAIL_MISMATCH`; cross-family/unknown resource: `404 NOT_FOUND`; expired/revoked invite: `410 INVITATION_UNAVAILABLE`; duplicate/conflicting operation: `409 CONFLICT`; rate limit: `429 RATE_LIMITED`.
- Unspecified `5xx` is a test failure, not a successful denial. Contract checks must assert both status and stable error code, plus unchanged membership/recipe state for denied writes.
</disposable_contract>
